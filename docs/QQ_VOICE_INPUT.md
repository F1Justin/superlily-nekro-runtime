# QQ 语音输入与普通回复

QQ 的 `record` 消息通过 QQ 原生或 MiMo ASR 转写，带 `[语音转写]` 标记进入原来的消息收集、人格、记忆、工具和普通回复路径。没有 TTS 或语音发送改动，不需要开启全局媒体归档。MiMo 路径通过 NapCat 获取 WAV，在内存中转交 ASR，不另存 Runtime 音频文件；NapCat 自身下载缓存仍存在。

## 启用

部署包含此变更的 Runtime 后，在 OneBot V11 适配器配置中设置：

- `VOICE_TRANSCRIPTION_ENABLED`: `true`（默认关闭）。
- `VOICE_TRANSCRIPTION_PROVIDER`: `napcat` 或 `mimo`。前者需要 `fetch_ptt_text`；后者需要环境变量 `QQ_VOICE_MIMO_API_KEY`，使用 `get_record` 转 WAV 和 `mimo-v2.5-asr`。
- `VOICE_TRANSCRIPTION_CHANNELS`: 如 `["group_123", "private_456"]`；空列表表示所有启用频道。
- `VOICE_WAKE_WORDS`: 莉莉建议 `["莉莉", "丽丽", "lily"]`；频道人格名称始终参与匹配。

匹配是大小写不敏感的名字包含检查，只表示呼叫候选，不判断语义上的称呼或转述；正文仍由现有模型处理。同音词需按真实转写结果配置，不改写转写原文。转写不能执行管理命令或消费命令等待输入。

没有名字、额外唤醒词或原有明确触发信号的语音仅进入历史，不通过随机或内容触发规则启动回复。现有频道禁用、旁观、用户权限、插件阻止和配额限制仍有效。明确的插件强制触发仍保留。

## 失败与限制

`napcat` 模式依赖非标准接口 `fetch_ptt_text`；当前生产已升级 NapCat 4.18.28，两个试用群选择 `napcat` 模式。失败、空结果或超时不会编造转写或发送错误消息；纯语音未能转写时沿用无法转换消息的跳过行为。识别服务按配置选择，不在失败后自动切换。原生接口的结果未就绪错误或空文本每秒重试，最多 6 次，总期限仍为 30 秒。

转写并发上限 2，排队和调用合计最多 30 秒，文本上限 4096 字符，MiMo 输入 Base64 上限 10 MiB。最近 5 分钟最多 512 个语音事件按机器人账号和消息 ID 去重，重启会清空。原 QQ 消息对象不改写，转写作为普通用户文本存储，扩展字段 `voice_transcript` 保留来源。不会插入伪造的 QQ @ 消息段。

## 验证

`poe test tests/test_qq_voice.py` 覆盖唤醒词、入口身份与原消息保留、禁用与频道范围、旁观、去重、失败/超时/取消、语音和普通文本触发差异。

上线验收需用户在启用频道发送两条实际语音：一条含“莉莉”，一条不含称呼，核对转写、只触发一次和普通回复结果。自动测试使用模拟 NapCat 响应，不能代表线上识别质量或部署成功。

回退：关闭 `VOICE_TRANSCRIPTION_ENABLED` 即停止新增语音转写，文字消息仍走原路径；必要时恢复上一 Runtime 镜像。

## 原音频输入

OneBot 的 VOICE_AUDIO_ENABLED 和模型组 ENABLE_AUDIO_INPUT 同时启用时，与文字上下文相同窗口内、当前或明确引用的 QQ record 音频由 get_record 转 WAV 后以 input_audio 送给模型。转写标为参考信息。所有已启用会话适用。每轮累计最多16分钟，按 WAV 帧数计算；优先当前、直接引用，再从近到远选择历史音频，按消息 ID 去重。单段仍受10 MiB Base64保护。超额或获取失败保留文字并标注未附加，历史音频随文字窗口退出。空转写保留音频引用，仍须显式唤醒。获取失败会向模型标明原音频不可用。不另存 Runtime 音频文件，不抓取音乐分享卡片。

当前已取消频道白名单（空列表表示全部已启用会话）。xiaomi-mimo 模型组启用原生音频，AUDIO_INPUT_DATA_URL=true；OpenRouter Gemini 使用默认纯 Base64 格式。非音频模型仍只使用转写，不强制替换模型。
